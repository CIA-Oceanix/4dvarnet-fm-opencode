## 2026-09-15: subgrad+state+xtau update_input (FourDVarNetPredictStateCFM only)

**Summary:** Added a new `update_input="subgrad+state+xtau"` mode, extending `subgrad+state`'s existing `[obs-x, x-Phi(x), x]` with a fourth channel `g_flow = x - beta_tau*x_tau`, for `FourDVarNetPredictStateCFM` only.

**Files modified:**
- `models/fourdvarnet.py` -- `_IMPLEMENTED_UPDATE_INPUTS`/`_PRIOR_MODES`/`_UPDATE_INPUT_CHANNEL_MULTIPLIER` (=4) gain the new mode; new `_CFM_ONLY_UPDATE_INPUTS` tuple. `_build_update_input`/`_solver_iteration` gain `x_tau=None, beta_tau=None` params (unused by every other mode, `FourDVarNetSolver` never passes them). `FourDVarNetSolver.__init__` explicitly raises `ValueError` if constructed with a `_CFM_ONLY_UPDATE_INPUTS` member (x_tau/beta_tau are structurally undefined there -- no outer flow-time exists). `FourDVarNetPredictStateCFM.forward` computes `x_tau_const` (the outer conditioning value, held fixed across the whole `K_inner` unroll -- distinct from `x`, which evolves every inner iteration) and `beta_tau = self.interpolant.beta(tau)` (the OUTER tau, not the inner iteration's own `tau_k`), passed to the `checkpoint(_solver_iteration, ...)` call as keyword args.
- `tests/test_fourdvarnet.py` -- new `TestSubgradStateXTau` class (8 tests): `FourDVarNetSolver` rejects the mode, channel multiplier is 4, forward shape/finite, gradients flow through the inner unroll, `_build_update_input`'s `g_flow` matches the exact closed form (and the other three channels are unchanged from plain `subgrad+state`), a missing `x_tau`/`beta_tau` raises, `x_tau` stays fixed across `K_inner` iterations (checked via a `K_inner=1` equivalence), checkpointed vs. uncheckpointed forward/backward match. Also fixes two real bugs found in the process in `_bypass_checkpoint` (the "no checkpointing" reference-run mock used by `TestGradientCheckpointing`/this new class): (1) it declared `**kwargs` but its body was `return fn(*args)`, silently dropping any kwargs -- real `torch.utils.checkpoint.checkpoint(function, *args, **kwargs)` forwards them to `function`, so this only surfaced now because `FourDVarNetPredictStateCFM.forward`'s new `x_tau=`/`beta_tau=` call is the first call site in this codebase to pass `checkpoint()` any kwargs beyond `use_reentrant`; (2) the naive fix (`return fn(*args, **kwargs)`) then broke on `use_reentrant` itself, which real `checkpoint()`'s own signature intercepts as a dedicated named parameter and never forwards to `function` -- fixed by giving `_bypass_checkpoint` an explicit `use_reentrant=None` parameter too, mirroring real `checkpoint()`'s signature so it absorbs but never forwards it.
- `config/experiment/FDV1CFM_predict_state_l96_subgradxtau.yaml`, `batch/run_l96_fdv1cfm_subgradxtau_train.sbatch` -- new diagnostic config/launcher (same base as the existing `FDV1CFM_predict_state_l96` M-tier UNet1D config, `update_input: subgrad+state+xtau` instead of `obs+state`).

**Rationale:** `reports/notes_4dvarnet_fm.pdf`'s "energy-informed parameterization" (Sec. 3.3) specifies three input terms for the CFM inner-refinement operator's residual update: `y-H(x^(k))`, `x^(k)-Phi(x^(k))` (both already `subgrad+state`'s own channels), and a third, `(alpha_tau^2*sigma_0^2)^-1 * (beta_tau*x^(k) - beta_tau^2*x_tau)` -- ill-conditioned as `alpha_tau -> 0` (`tau -> 1`, dividing by a vanishing squared term). Per explicit user direction, this implementation drops the `(alpha_tau^2*sigma_0^2)^-1` prefactor entirely and feeds the un-prefactored core `x^(k) - beta_tau*x_tau` instead -- bounded/well-conditioned everywhere on `tau in [0,1]` since `x`/`x_tau` are both state-scale and `beta_tau in [0,1]`. This is the CFM-native analog of the `subgrad+state`-vs-`grad+state` investigation this branch has been running for the plain (non-CFM) unrolled solver.

Caveat: `FourDVarNetPredictStateCFM` has no `monai` backbone option today (UNet1D only), so this run is comparable only to the existing M-tier UNet1D `FDV1CFM_predict_state_l96` baseline, not to this investigation's S-tier MonaiUNet1D runs.

**Verification:** `pytest tests/test_fourdvarnet.py -q` (112 passed, default env) and `pytest tests/test_fourdvarnet_monai.py tests/test_lightning_module.py -q` (44 passed, monai env, from the immediately preceding `prior_output_init_std`/`detach_var_cost_grad` work -- `models/fourdvarnet.py`'s monai-relevant code paths are unaffected by this change).
